# 故障分类规则（主诊断与结构化抽取共用）

先依据本案日志确定首个故障及因果链，再选择类别。工具执行失败只能说明取证缺口，
不能据此判定被测系统故障。用例名称、知识库案例、错误码的 probable_component 只作路由旁证。

- `version`：有版本号、协议修订、schema、校准数据版本或兼容性不匹配的直接证据。
  握手超时、连接失败、没有 ACK 本身不足以判定版本问题；不要把所有“协议流程异常”归为版本。
- `case`：用例脚本错误，或输入参数、配置组合违反明确约束，例如缺必填参数、非法带宽/SCS、
  重复标识。区分“输入不合法”和“输入通过后运行环境失效”。
- `env`：连接、网络、资源、时钟或运行状态故障，且没有更直接的版本或用例错误证据。
  包括时钟失锁、运行资源耗尽、前传丢包、订阅/路由未建立；不能无证据猜测底层软件版本缺陷。
- `none`：最终检查明确正常，或同一对象的故障之后出现明确恢复、闭环且没有随后失败。
  必须对齐组件、流水线、cell/peer/topic/direction 等对象标识及时间顺序；较早正常、其他对象的
  ACK 或单独一条 ACTIVE 不能抵消本案故障。此时 root_component=none，root_cause=none，保留恢复证据。
- `unknown`：本案证据不足，或关键矛盾尚未解决。只将有争议的字段设为 unknown，说明缺口；
  不为了填齐字段把不确定性强行分配给 version/case/env。

root_component 指因果链中首个故障组件，不是最后出现级联 ERROR 的组件。
根因类别与根因组件分别判断：可以找到组件但无法确定类别，或确定类别但无法确认组件。
ERROR/WARN 的数量不决定根因；保留正常、否定、恢复和反证，不能只摘支持当前假设的句子。
